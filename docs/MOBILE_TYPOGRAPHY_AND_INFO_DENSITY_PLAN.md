# FM-League 移动端字号与信息编码适配 · 完整方案

> 版本 v1.0 · 2026-11-27 · 覆盖 12 个页面 + 6 个弹窗（18 个文件，16,749 行）
> 目标：在**不减少任何数值、不增加任何点击**的前提下，让手机端数值可读、可扫、可比较。

---

## 0. 结论先行

上一轮"全局阶梯放大字号"的做法方向错误，原因有三：

1. **字号放大了，容器没放大**。`mobileFontSize()` 把 ≤9px 提到 11.5px、≤12px 提到 14px，但所有页面坐标硬编码在 1280×720 基准上，容器宽度分毫未动。结果是溢出、截断、重叠，而不是更清晰。
2. **FM 的核心是数值密度**。把信息折进二级页会多一倍操作，等于杀死玩法。信息一条都不能删。
3. **真正的问题是编码方式，不是字号**。18 个文件里绝大多数数值是"标签+数字"的纯文本平铺（`射门 71`、`CA 68`、`12场`），所有数值视觉权重相同，玩家必须逐字读才能比较。

**本方案的核心：不删数值、不改坐标体系、不增加点击，改用分层视觉编码——核心决策值放大并加色条，次要值压缩成缩写标签但仍全部平铺，比较靠图形不靠读数字。**

---

## 1. 根因：三层缩放与一个错配

### 1.1 真机缩放链路

| 层 | 值 | 说明 |
|---|---|---|
| 设计稿 | 1280×720 | `THEME.W/H`，所有坐标硬编码于此 |
| Canvas 内部 | 1600×900 | DPR 1.25 封顶（`main.ts applyHiDPI`） |
| CSS 显示 | `min(100vw, 100vh×16/9)` | 等比塞进手机横屏 |
| 字号 | `mobileFontSize()` 放大 1.5~2 档 | 只有字号变，上面三层坐标都不变 |

**错配**：字号按"放大后"渲染，布局按"原尺寸"排布。这是所有溢出风险的唯一根源。

### 1.2 实测数据（真机 OPPO PHY110 / Android 16）

- 设计 11.5px → 屏幕约 6~7px（阶梯补回一部分，仍偏小）
- Canvas 1600×900，截图确认字体放大适配已生效但密度未变
- 数值可读性问题集中在 ≤12px 的高频小字（多数页面占比 60~72%）

### 1.3 现有保护机制盘点

| 机制 | 覆盖 | 缺口 |
|---|---|---|
| `drawButton` 热区 pad 到 44px | 所有按钮 | 手动 `hits.add()` 不受保护 |
| `fitText` 省略号截断 | 显式调用处 | 大量 `drawText` 长句未调用 |
| `drawWrappedText` maxLines | 显式调用处 | 行高被移动端强制拉大，行数不变 → 截断 |
| `drawBadge` 自动降档 | badge 内部 | 最低到 8px，仍偏小 |
| `nodeHitR = max(r+10,22)` | MetaScreen 节点 | 其他页面手动热区无此保护 |

## 2. 全局规范（先定标准，再逐页改造）

### 2.1 字号分层 Token——替代粗暴阶梯

不再用"按数值分档放大"，改为**按语义分配档位**，每档在设计时就已考虑容器宽度：

| Token | 字号 | 用途 | 移动端 |
|---|---|---|---|
| `DISPLAY` | 28~34 | 比分、终章标题 | 不放大 |
| `HEADLINE` | 20~24 | 核心决策值（CA/身价/评分）、页面标题 | +0~2 |
| `TITLE` | 15~16 | 卡片标题、球员名 | +1.5 |
| `BODY` | 13~14 | 正文、数值标签 | 已为放大后基准 |
| `LABEL` | 11.5~12.5 | 次要字段、缩写属性 | 已为放大后基准 |
| `MICRO` | ≥11 | 角标、脚注 | **硬下限，不得更小** |

关键改变：`mobileFontSize()` 保留为兜底，但新代码一律显式使用 Token，杜绝"9px 放大到 11.5px 却不知道容器够不够"。

### 2.2 数值编码组件库（新增，全局复用）

| 组件 | 签名 | 作用 |
|---|---|---|
| `drawStatBar` | `(ctx, value, max, x, y, w, h, color)` | 色条编码，替代纯数字比较 |
| `drawCompactStat` | `(ctx, label, value, x, y)` | 缩写标签+数字，如 `射71` |
| `drawDeltaBadge` | `(ctx, delta, x, y)` | 升降箭头色块，替代 `+3/-2` 文本 |
| `drawRankTile` | `(ctx, rank, tier, x, y)` | 排名分级色块 |
| `addTouchTarget` | HitsRegistry 方法 | 手动热区自动 pad 到 44px |

### 2.3 字段名压缩对照表（信息量不变，宽度减半）

| 现状 | 改造后 | 宽度节省 |
|---|---|---|
| `射门 71` | `射71` | 40% |
| `CA 68` | `68` + 色条 | 50% |
| `年龄 24` | `24岁` | 33% |
| `12场 / 3.4km` | `12 / 3.4` | 30% |
| `体能 68%` | 色条 + `68` | 35% |
| `进球 3 / 助攻 2` | `3 / 2` + 微图标 | 45% |

FM 老玩家对缩写零认知成本，PC 端同样受益（扫视比较更快）。

### 2.4 热区规范

真正 <44px 的只有 4 类手动 `hits.add()`，全部纳入 `addTouchTarget`：

| 位置 | 现状 | 改造 |
|---|---|---|
| PlayerModal 号码格 | 28×25（33 个） | 44×44 |
| PortalScreen 侦察沙盘点 | 38×38 | 44×44 |
| TitleScreen 调色板 | 32×30 | 44×44 |
| MatchDay 场上球员点选 | 28×28 | 44×44 |

## 3. 逐页面改造方案

> 标注说明：**密度** = 同屏最多条目数；**小字占比** = ≤12px 字号调用占比；**风险** = 放大后最高溢出点。

### A 类 · 数值密集核心页（7 个 = 6 页面 + 1 弹窗，重点改造）

#### 3.1 ClubRosterScreen · 引援中心（1253 行）

**现状**
- 密度：19 条（左 10 榜单行 + 右 9 球员卡），每卡 11 个数值字段
- 小字占比：约 60%（9 / 9.5 / 10 / 10.5 / 11 / 11.5 / 12）
- 风险：转会窗横幅长句无 fitText 必撞按钮；榜单名字与 `X岁 · CA 68 / PA 80` 互挤；球员卡长名撞 CA
- 热区：榜单行 292×36、榜单 tab 92×23、筛选 54×24、排序 42×24

**改造**
1. 球员卡：CA/PA 改为 `HEADLINE` 等宽数字 + `drawStatBar`；6 属性统一用 `drawStatMicro`（已是正确范式，推广到全部卡）；特质 `fitText`
2. 榜单行：名字与 CA/PA 分行；年龄用 `24岁`；热区高 36→44
3. 转会窗横幅：长句改 `drawWrappedText` 2 行，或拆成短句 + 第二行按钮
4. 筛选/排序 tab：接入 `addTouchTarget`

**验收**：真机截图确认 9 张卡数值可读、横幅不重叠、榜单无挤压。

#### 3.3 MatchDayScreen · 比赛日（4145 行，最复杂）

**现状**
- 密度：22 场上球员 + 18 条解说 + 4 手牌 + 9 行统计 + 4 预案
- 小字占比：极高（7.5 队长角标、8.5 role 标签/手牌脚注、9.5 球衣号码、9.2 替补属性、11 解说）
- 风险：解说硬编码 14px 行距，放大后行距=字高；场上 role 标签胶囊按 8.5px 算宽，放大后互叠；全场统计单行 11px 塞 776px 无 fitText；手牌 90×100 内 6 行文字行距固定 15px
- 热区：**场上球员点选 28×28（严重不足）**、换人列表 214×24、预置战术 158×40、播控 82×36

**改造**
1. 场上球员：圆点半径 10.5→13，号码 9.5→11px，体能条 20×3→24×4，**点选热区 28×28→44×44**；role 胶囊按实际字号算宽并扩大碰撞避让半径
2. 解说：行高 14→动态 `max(18, fontSize×1.35)`；条数 18→12（保留最新，旧的可上滑查看）；`boxH` 按新行高重算
3. 手牌：行距 15→18，必要时卡高 100→112；脚注 8.5→11
4. 右栏统计：保留双色条；数值 `HEADLINE` 等宽；行距 58→62
5. 全场统计单行：拆 2 行或强制 `fitText`
6. 次级按钮（播控/换人/筛选）：接入 `addTouchTarget`

**验收**：真机跑完整一场，解说不重叠、球员点选准确、手牌文字不溢出。

## 6. 验收标准（统一）

1. **信息完整性**：改造前后数值字段数一致，不得有任何删减
2. **操作次数**：核心页到达任一数值的点击次数不得增加
3. **可读性**：真机截图上 `LABEL` 档（≥11.5px）在 30cm 握持距离可清晰辨认
4. **无溢出**：所有长文本不出现 `…` 截断（除设计上允许的卡片摘要）
5. **热区**：所有可点元素 ≥44×44
6. **PC 兼容**：桌面端不受负面影响（色条与缩写在 PC 上同样提升扫视效率）

---

## 7. 一句话总结

问题不是"字太小"，是"1280×720 的桌面信息密度硬塞进手机 + 所有数值同等视觉权重"。解法不是删数值、不是换坐标系、不是全局放大字号，而是**在固定密度内重新分配视觉权重**：核心值放大加色条、次要用缩写平铺、比较靠图形不靠读数字。18 个文件逐页落地，P0~P4 五阶段推进。
